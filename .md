- business logic inside usecase
- DB logic inside repository

# 9. Outbox Pattern

# Problem

Prevent DB/Kafka inconsistency.

# Solution

Use transactional outbox.

## Schema

```sql
CREATE TABLE outbox (
  id UUID PRIMARY KEY,
  aggregate_id UUID,
  event_type TEXT,
  payload JSONB,
  processed BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP
);
```

## Flow

```txt
DB transaction
 ├── update payment
 └── insert outbox row
        ↓
outbox worker
        ↓
Kafka publish
```

## Payment lifecycle extensions

- Refund saga: `refund.requested` → `provider.refund` → `refund.completed` → `ledger.compensation`

- Tokenized payment methods (`payment_methods` table)
- Multi-currency via `shared/fx`
- Disputes table and `DISPUTED` status
- `payment.completed` event after successful saga

## Provider & ledger

- PayPal mock adapter
- `GET /ledger/export` for reconciliation
- Compensation entries (`is_compensation`, `entry_type`)

## Fraud

- Risk score on validation
- Device ID, country, IP velocity
- Redis blocklists (`POST /fraud/blocklist`)

## Gateway & security

- Circuit breaker for payment upstream
- RBAC: refunds and `/admin/*` require `admin` role
- Merchant API: `GET /merchant/payments`
- Audit events table

## Reconciliation

- `POST /reconcile/auto` — fetches ledger from ledger-service

## Notifications

- Email/SMS channels (log-based; enable via env)
